## P2: конкурентная регистрация после удаления аккаунта

[Серверный patch и инструкция](../../server-patches/account-deletion/README.md)
исправляют `SaveDevice` на backend `9e6058c31cc07bff0f48d8f7f6a40106c55c4881`.
Регистрация блокирует строку пользователя до UPSERT и повторно проверяет состояние
в этой же транзакции. Блокировка согласована с `DeleteAccount`. Удаление первым
даёт поздней регистрации HTTP401; регистрация первой завершается до удаления,
после которого не остаётся строки устройства. Tombstone не даёт права записать
новый token. Новых endpoint, форматов ошибок или migrations нет.

На реальном PostgreSQL17 воспроизведены ошибки исходного кода и проверены оба
порядка транзакций для физического удаления и tombstone. Фактическое ожидание
подтверждается `pg_blocking_pids`, не задержкой по таймеру. Проверены также
active/missing/tombstone/blocked/guest и существующий HTTP mapper.

- До исправления: **8 FAIL / 1 PASS** из 9 новых сценариев.
- После исправления: **9/9 PASS**,0 SKIP; четыре наблюдённые зависимости блокировок.
- Смежные проверки с `-race`: **15 верхнеуровневых тестов и 27 вложенных сценариев PASS**,0 SKIP; вложенные не суммируются с родительскими.
- Независимое применение опубликованного patch к чистой временной копии pinned
  source и повтор с `-race`: **9/9 PASS**,0 SKIP; [receipt](evidence/p2-backend-reproduction/receipt.json).

Статус: **исправление реализовано и проверено в patch; требуется интеграция и выпуск backend**.
Исходный сервер `9e6058c` без patch сохраняет дефект. Обновление iOS самостоятельно
не устраняет межклиентскую серверную гонку. Уже начатая доставка через внешний
push gateway и реальная APNs-доставка не проверялись этим набором.

## P2: восстановление локальной очистки после отказа хранилища

После подтверждённого DELETE200 приложение сохраняет запись `origin + userID`
в отдельном Keychain item с `WhenUnlockedThisDeviceOnly` и `Synchronizable=false`,
перед удалением записи из push-журнала. Запись не содержит credentials, OS token,
имя или email. При временном отказе записи выполняется один ограниченный повтор;
неподтверждённая запись остаётся в памяти для следующего вызова очистки.

При `attach`, новой регистрации или `retryCleanup` сначала восстанавливается
локальная очистка подтверждённых scopes. Это работает после перезапуска,
при уже загруженном журнале и без активного аккаунта. Только подтверждённые
записи удаляются; другой пользователь или тот же UUID на другом сервере сохраняются.
401, timeout и обычный logout не создают подтверждения удаления.

До чтения общего ledger сначала сохраняются ожидающие подтверждения в памяти:
однократная ошибка последующего чтения не должна лишать приложение proof.
После awaited pre-POST записи повторно проверяются epoch, enabled intent и
удалённый scope, поэтому устаревшая операция не начинает новую регистрацию.

`IdentityModel` проверяет сохранённое подтверждение до восстановления старого
аккаунта, включая offline-путь. Остаточные credentials, индекс и cache повторно
очищаются без повторного DELETE. Подтверждённое серверное удаление не объявляется
неуспешным из-за ошибки локального хранилища.

Старый JSON-журнал без нового поля читается с пустым списком подтверждений.
Протокол хранилища имеет реальную journal-backed реализацию для существующих
in-memory/custom stores. Keychain использует отдельный item; его read-modify-write
выполняется без suspension внутри actor. Подтверждения сохраняются для блокировки
восстановления удалённого scope; предел 1000 уникальных записей проверяется без
автоматического удаления доказательств. Минимальные origin/UUID остаются локально
и не отправляются на сервер.

Если **все** попытки durable-записи отклонены и процесс завершён до восстановления
хранилища, сохранить полученный ответ невозможно. В таком случае неизвестная
push-привязка остаётся заблокированной: отсутствие proof не подменяется ответом401.
Это не выдаётся за успешное восстановление при полной потере возможности записи.
